LAB: TRAVERSAL SEQUENCES STRIPPED WITH SUPERFLUOUS URL-DECODE

Abrir PDF ↗

Previsualización de la Investigación

OBJETIVO

Actualizar la guía del laboratorio FILE PATH TRAVERSAL — TRAVERSAL SEQUENCES STRIPPED WITH SUPERFLUOUS URL-DECODE para que cubra técnicas de bypass basadas en secuencias anidadas y codificación URL múltiple. El objetivo sigue siendo explotar una sanitización no recursiva y/o un proceso de decodificación excesiva para leer archivos sensibles como /etc/passwd.

AMBIENTE DE LABORATORIO

Localizar la petición GET que contiene filename=blog.png o similar.

Probar secuencias simples: reemplazar filename por ../../etc/passwd o /etc/passwd.

Probar secuencias anidadas: enviar filename=....//....//etc/passwd. Resultado esperado: si el filtro es no recursivo, la petición resuelve y devuelve el contenido de /etc/passwd.

Probar bypass con codificación URL simple: enviar filename=%2e%2e%2f%2e%2e%2fetc%2fpasswd. Si el servidor decodifica una vez y luego aplica el filtro, puede bloquearlo; si decodifica de forma inadecuada, puede permitirlo.

ANÁLISIS DE LA VULNERABILIDAD Y FORMA DE RESOLUCIÓN

Comportamiento inseguro observado

  • El servidor aplica reemplazos simples para ../ o realiza una única pasada de decodificación.
  • La sanitización no es recursiva y/o el servidor realiza decodificaciones múltiples en momentos distintos del pipeline, lo que permite que payloads especialmente construidos se transformen en secuencias ../ válidas tras el procesamiento.

Por qué funcionan las técnicas

  • Secuencias anidadas: ....// contiene .. y // de forma que, tras eliminar una porción no recursivamente, los fragmentos restantes se concatenan formando ../.
  • Doble codificación: si el servidor decodifica más de una vez o decodifica en etapas, una entrada doblemente codificada puede evadir la detección inicial y convertirse en ../ después de una decodificación intermedia.

Mitigaciones recomendadas

  • Canonicalizar rutas usando funciones nativas del sistema (por ejemplo realpath, Path.resolve) y comparar que la ruta resultante esté dentro del directorio base autorizado.
  • No confiar en reemplazos de cadenas; evitar sanitizaciones basadas solo en replace("../","").

COMANDOS Y HERRAMIENTAS UTILIZADAS

  • Burp Suite – Proxy (Intercept ON): captura de peticiones HTTP generadas por el navegador.
  • Forward: permitir que la página cargue después de interceptar las solicitudes.
  • Observación de tráfico GET: identificación de peticiones hacia recursos estáticos.
  • Prueba de acceso a directorios: navegación hacia niveles superiores (../).
  • Send to Repeater: envío de la solicitud del parámetro filename al entorno de pruebas.
  • Manipulación de parámetro GET (filename): modificación con secuencias anidadas no recursivas (....//).

RESULTADOS

Se identificó que la aplicación web implementa una sanitización débil basada en expresiones regulares o reemplazos simples que operan de forma no recursiva.

Se comprobó que el uso de payloads anidados (....//) permite superar el bloqueo de secuencias simples de tipo ../.

Con filtros no recursivos y/o decodificación superflua, payloads como ....//....//etc/passwd o variantes doblemente codificadas pueden permitir la lectura de /etc/passwd. Burp Repeater acelera la iteración de payloads y la confirmación del bypass.

CONCLUSIONES

Las funciones de sanitización que eliminan cadenas prohibidas (como ../) sin aplicar un bucle recursivo hasta que no queden coincidencias son altamente vulnerables a técnicas de anidación de caracteres.

La combinación de secuencias anidadas y codificación URL múltiple es una técnica efectiva contra filtros débiles. La defensa robusta requiere canonicalización, listas blancas y validación post-normalización.
